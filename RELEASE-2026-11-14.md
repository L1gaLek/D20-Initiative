# Multiplayer, map navigation and token access — 14 November 2026

## Changes

- All initiative buttons use a confirmed, token-specific HTTP mutation, followed by a WebSocket broadcast to the room. A failed request leaves the character available to roll again and displays an error. The dice log is emitted after confirmation.
- The individual/all-owned buttons previously sent `inCombat` in a player state patch. The backend required GM privileges for that field even when it was unchanged, and the client suppressed that error. Legacy clients can now repeat an unchanged selection but cannot change it. The new client omits GM-only selection fields.
- Initiative epochs are saved with each map. WebSocket commands from one connection execute in order.
- Hold the middle mouse button and drag to pan, with animation-frame interpolation. This works in top-down and isometric modes; Ctrl + middle button retains the existing isometric rotation gesture.
- Offscreen bases have orange indicators. Offscreen allies have green indicators and token names. Hidden tokens and tokens on other maps do not produce ally indicators.
- Character and monster sheet headers contain token access controls. GM can transfer ownership of any token. The owner or GM can grant one other room participant control, or revoke it by selecting “Только владелец и ГМ”. Delegates can move the token, edit its sheet and roll for it; ownership remains with the owner. Delegates cannot pass control onward.
- Ownership transfer clears delegated control and immediately revokes the old owner's edit/play permissions. Token rows on every map receive the new owner in the same transaction as room state. Editor input is included in the handover transaction; older snapshots cannot undo a newer access change.

## Validation

- `npm test`: syntax checks and 20 regression tests.
- `npm --prefix backend test`: backend syntax check.
- `npm run test:browser`: five independent browser contexts, real frontend scripts and HTTP/WebSocket traffic, backed by the production mutation functions and an isolated transaction adapter. Covers rejected/confirmed initiative, all three roll buttons, GM combat transition, delegated movement/dice/sheet saving, base and monster transfers, immediate revocation, stale snapshots, offscreen arrows and smooth panning in both views.
- Browser tests do not connect to production accounts or modify live player data. Their database and membership adapters are test doubles; deployment health/source verification is separate.

To run browser tests, install backend dependencies and Playwright 1.56.1 in a local development environment, then run `npm run test:browser`. `D20_PLAYWRIGHT_MODULE` can point to an external Playwright module, and `D20_BROWSER_PATH` can select an installed Chromium browser. `D20_SCREENSHOT_DIR` optionally stores UI screenshots.

## Deployment

The primary frontend is GitHub Pages. The backend deployment updates only `server.js`, after a source hash check and backup; `.env`, PM2 configuration, uploads and database schema are preserved. No database migration is needed: access fields live inside the existing room-state JSON.

All participants should reload the page with Ctrl+F5. Start a fresh initiative phase for the next check: previously rejected results existed only in those clients and cannot be reconstructed reliably from the saved combat state.
